# Vorlyn

Multi-tenant collaboration tool where teams review, comment on, and hand over markdown documents — typically generated by coding agents — with part-level commenting on text and diagrams, and an MCP server so agents are first-class participants in the feedback loop.

## 1. Core Principles

1. **Tenant isolation is absolute.** No code path may return another organization's data. Isolation is enforced by the database (Postgres row-level security on every tenant-scoped table), not by application-code discipline. A cross-tenant leak is the worst-case failure of this product.
2. **Comments never lie.** A comment always highlights the exact text or diagram part it was made on. Comments pin to an immutable document version; re-anchoring across versions is confidence-scored, and a comment that cannot be re-anchored is shown honestly as orphaned — never silently attached to the wrong text.
3. **No org data in logs or telemetry.** Logs and metrics carry opaque IDs and operational metadata only. Document content, document names, user names, emails, and comment text never appear in logs, traces, metrics, or error reports.
4. **Fully mobile responsive.** The web app works on any viewport, phone to desktop — no desktop-only flows, no feature that's unreachable on mobile. Every screen ships responsive; "mobile is a later phase" is not a valid excuse for a merge.
5. **Deployments are zero-downtime.** Production releases never interrupt service. Blue-green (or an equivalent health-gated rolling cutover) is the only deploy path: new capacity comes up and passes health checks before old capacity drains, and a failed health check rolls back automatically, without a human in the loop. No maintenance windows for routine releases (ADR 0006).
6. **Database migrations are always backward-compatible.** Every migration must work with the old and new application code running at the same time — deploys and migrations are decoupled, never atomic together, because a rolling/blue-green deploy always has both versions live briefly. Destructive cleanup (dropping a column or table a prior migration made obsolete) ships as its own later migration, only once nothing still reads or writes the old shape anywhere. The database is never left in a state only one app version can tolerate (ADR 0006).

## 3. Code Standards

- **Zero-tolerance lint**: zero ESLint errors and zero TypeScript errors (`strict: true`) on every commit; CI blocks on both. Prettier enforced — no style debates.
- **Coverage**: ≥95% lines and branches on domain and application layers. Coverage is a floor, not a target to game — assertions must be meaningful.
- **Money paths in Gherkin**: quota enforcement, retention/purge, permission checks, sharing rules, and tenant isolation are specified as Gherkin scenarios (`features/`) and executed as living documentation.
- **Naming**: kebab-case filenames; PascalCase types/components; camelCase functions/variables; hexagonal seams named explicitly — `*.port.ts` (interfaces) and `*.adapter.ts` (implementations).
- **Architecture rules (CI-enforced via dependency-cruiser)**:
  - Domain layer imports nothing from adapters, frameworks, or SDKs.
  - No business logic in React components or HTTP route handlers.
  - Every DB access goes through a repository; no inline SQL outside the persistence layer.
  - Every repository method executes inside a tenant context (RLS session variable set) — no bypass path exists in application code.
- **Docs**: doc comment on every port interface and public domain function. Architectural decisions recorded as ADRs in `docs/adr/`.

## 4. Security Non-Negotiables

- **Secrets**: live in whatever secrets store a deployment brings, injected at deploy time. Never in git, logs, client bundle, or SQL. Local dev uses gitignored `.env`.
- **Authentication**: every API route requires an authenticated session except health checks and auth callbacks. Share-link access still resolves to an org-scoped grant — a link never bypasses tenant isolation.
- **Authorization**: org settings, retention config, immediate purge, and role changes are admin-only. Only a document's owner can resolve comments (per org sharing policy).
- **Storage**: all S3 access via short-lived signed URLs; buckets are never public.
- **Sessions**: httpOnly + Secure + SameSite cookies; stateless signed session token, 24h global ceiling, organization-configurable shorter max (`organizations.session_max_hours`, 1–24h) applied at decode time, silent refresh past half lifetime (ADR 0005).
- **CSRF**: signed double-submit token (`vorlyn_csrf` cookie = `HMAC(secret, session_cookie_value)`, echoed into `x-csrf-token` header on mutations) plus an Origin allowlist on every mutating request as a second layer; `SameSite=Lax` as a third (ADR 0005). MCP, webhook, and public-hub routes are exempt (no cookie session to forge against).
- **Abuse controls**: server-side rate limiting; upload cap 500KB/file, content-policy validated (binary-signature/control-byte/replacement-density rejection — ADR 0011, since there is no such thing as "invalid markdown" to parse-validate against); per-user weekly and monthly upload quotas; all enforced in the domain layer, not just the UI.
- **Never bypassable**: RLS active on every tenant-scoped table; the application connects as a non-superuser role that cannot skip RLS; the MCP server goes through the identical domain layer and permission checks as the HTTP API.
- **Audit log**: deferred past MVP (schema designed so it can be added without migration pain).

## 5. Architecture Invariants

- **Monorepo layout**: `packages/shared` (DTO types crossing the transports), `packages/domain` (pure TypeScript — zero framework/SDK imports), `packages/app` (use-cases + port interfaces), `packages/persistence` (Postgres repositories, migrations, storage/telemetry adapters), `packages/api` (Fastify HTTP adapter, and the `ServerExtension` seam a deployment composes onto), `packages/mcp` (MCP server adapter), `packages/jobs` (standalone compliance-sweep scheduler), `packages/cli` (the `vorlyn` sync CLI), `packages/web` (React SPA, a standalone leaf with zero `@vorlyn/*` runtime imports — the dependency-cruiser `web-frontend-only` rule). Nine packages, all of them core; this repository ships no cloud-provider IaC — a deployment brings its own (§7).
- **API/MCP parity**: HTTP API and MCP server are thin transports over the same application services. A capability existing in one and not the other is a bug, not a roadmap item.
- **Storage boundary**: Postgres holds metadata, comments, shares, quotas. S3 holds immutable version blobs only. Document content never enters Postgres (only content hash + byte size); metadata never lives in S3.
- **Immutable version content, tombstone-on-purge** (ADR 0001): every upload creates a new version row + new S3 object; content is never mutated in place. A blob may be deleted by retention policy, in which case the version row persists as a tombstone (`purged_at` set; id, org_id, hash, size, timestamps kept) — comments keep valid FKs and truthful anchor-stored quotes, and diff/re-anchor against a tombstone reports "version purged" honestly. Version rows are never deleted. No history UI required — versions exist so comments survive agent re-uploads (Core Principle 2).
- **Anchor model**: comments store W3C-style selectors (exact quote + surrounding context + position hint for text; source-level names for diagram parts) as JSONB. Re-anchoring across versions is confidence-scored; below threshold → honestly orphaned, never guessed.
- **Data flow**: all I/O async; React state flows down, events up; domain errors are typed results, not thrown strings.
- **Expand/contract migrations** (Core Principle 6, ADR 0006): every schema change ships as expand (additive: new nullable column, new table, new index — safe for old code to ignore) fully rolled out and soaking, _then_ contract (the destructive step: `NOT NULL`, `DROP COLUMN`, `DROP TABLE`) as its own separate migration once no running instance can hit the old shape. A single migration is never both. Forward-only (`schema_migrations`, no down-migrations) — a bad expand step is fixed by a new migration, not a rollback of the schema underneath a rolled-back deploy.

## 6. Data & Privacy

| Data                                        | Where stored                          | Third parties                | Retention                                                                                                                                                                                                                                                           |
| ------------------------------------------- | ------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Document content (versions)                 | Object storage, encrypted at rest     | Never                        | Tiered: soft-delete window + version auto-purge per the retention profile on the org's tier (`packages/domain/src/tier.ts`, ADR 0001 — a self-hosted org gets unlimited ceilings); org admin can purge immediately; deployment's own backup policy governs the rest |

| Sessions                                    | Cookie + WorkOS                       | WorkOS                       | Session lifetime                                                                                                                                                                                                                                                    |
| Operational logs/metrics/traces             | Behind `TelemetryPort` (OTel adapter) | Never                        | 30 days; opaque IDs only (Core Principle 3)                                                                                                                                                                                                                         |

**Never sent anywhere**: document content and comment text never leave our infrastructure — no third-party analytics on content, no LLM calls, no external search indexing.

## 7. Licence and boundary

- **This repository is the source of truth for the core, and it is public**, under **Apache-2.0**
  (see `LICENSE` and `NOTICE`) — chosen for its patent grant and its explicit trademark non-grant.
  Anyone may fork, self-host, or resell this code; only the original project may call a hosted
  offering by its public name. Self-hosting is a supported, first-class use: `SELF_HOSTING.md`.
- **A concept the core does not need does not live in the core.** Stated as a test, not a list, and
  applied whenever deciding whether a change belongs here at all. Billing, payment providers,
  subscription lifecycle, and any cross-org staff console are out of scope — not a port, not a stub,
  not a null object; the concept simply does not appear. Org-scoped self-administration and the
  tier/quota domain logic are genuinely core and stay here — a self-hosted org's ceilings are
  unlimited, so the machinery is inert rather than crippling.
- **Where the core must state a fact a deployment may act on, it states the bare fact through a
  narrow port it owns, defaulting to a no-op.** `SeatSyncPort.onSeatsChanged(org,
humanMemberCount)` is the worked example: no billable seats, no customers, no subscriptions
  appear in it, and a self-hoster configures nothing.
- **Extension is a designed seam, not a patch.** A deployment adds routes through `ServerExtension`
  (`packages/api/src/server-extension.ts`), which exposes three registration positions differing in
  which core guards have already run, and which this repository owns and tests. Changing it is
  changing public API — treat it as such.
- **Migrations are forward-only and never renumbered**, so a column or table a removed feature once
  owned can outlive the feature as inert residue rather than being retrofitted away (ADR 0006).

## 8. Delivery Workflow (how we build)

1. **Phased delivery**: work proceeds in phases; each phase ends compiling, tested, and locally runnable. No phase merges red.
2. **Per-phase gates** (standing rule): zero lint/type errors → ≥95% domain/app coverage → Gherkin money-path scenarios green → integration tests against real Postgres (ephemeral per-run database, `createTestDb`, ADR 0005) → Playwright e2e for user-visible flows → local security scan.
3. **Tenant-isolation tests are mandatory in every phase that touches data access**: a test proving org A cannot read org B via API, MCP, and direct repository call.
4. **Externals mocked in unit tests** (WorkOS, S3), real in integration tests (ephemeral per-run Postgres via `createTestDb`, filesystem storage adapter — no LocalStack, ADR 0005).
5. **ADR before deviation**: any change to Sections 1–7 requires an ADR and an explicit human OK.
6. **Production readiness is the deployment's gate, not the core's.** This repository ships a core, not a running service: it has no cloud account, no alerting and no connection math to get right, so it defines no production-readiness checklist of its own. Anyone operating this code owns that gate for their own deployment. What this repository owes them is that rules 1–5 above are true of every commit on `main`.

## 9. MVP Scope (locked)

Core: org onboarding, upload (drag-drop, 500KB cap, content-validated, quotas), projects + unfiled docs, beautiful markdown rendering (mermaid, GFM), part-level comments on text and diagram parts, threads + resolve, minimap (color-coded: open / replied / resolved), sharing per org policy (link-based or directory-scoped), roles (admin/member; grants carry read / comment / share / edit — ADR 0008, ADR 0014, where `share` buys creating/revoking grants on the document (capped at the granter's own held level) and `edit` inherits `share` by lattice plus buys new versions; document management stays owner-or-admin), retention (30-day soft delete, org purge override), immutable versions.

Promoted from dreaming:

- **MCP feedback bundle**: one MCP call returns all unresolved comments + quoted text + thread + anchor context, shaped for agent consumption; agent replies/resolves via MCP after re-upload.
- **Deep links to anchors**: permalink opens doc scrolled to highlighted range/diagram part.
- **Version diff view** (ADR 0003): rendered markdown diff, "what changed since my comment."
- **Search**: Postgres FTS over docs the user owns or has access to — permission-scoped, never org-wide by default.
- **Summary signals**: per-file and per-project rollups on homepage — total / open / resolved comment counts.
- **Project color coding**: user-assignable project colors surfaced across homepage and doc lists.
- **Sign-off workflow** (ADR 0002): version-pinned reviewer requests + approve/changes-requested verdicts; document status always derived from active requests and the current version's approvals, never stored. Org-configurable `approval_gate` (soft warns, hard blocks approval while comments are open). Guests with a comment grant may be requested reviewers and submit verdicts — a verdict is annotation, never a document mutation, so the guest hard rule below is untouched structurally.
- **Suggested edits** (ADR 0002, accept reworked by ADR 0007): a comment subtype (`kind: suggestion`) carrying proposed replacement text — inherits anchors, re-anchoring, threading, caps, soft delete, and the guest allowlist unchanged. Accepting is metadata-only (owner-or-org-admin only, unchanged gate): it flips the outcome to accepted, no splice, no new version. Materialization is detected lazily by the existing re-anchor pipeline, when a later real edit's content exactly matches the proposal at the resolved range; until then it stays "accepted, pending." Guests may create suggestions (comment permission), never accept or reject them — the guest hard rule below is untouched structurally.
- **Grantable edit rights** (ADR 0008): `share_grants.permission` is `read | comment | edit`. An `edit` grant buys `uploadNewVersion` and nothing else — delete/archive/move, resolve, re-share, review requests, and suggestion accept/reject all stay owner-or-org-admin behind `canManageDocument`, which this ADR deliberately does not touch. Grantable on named user grants only, not share links (policy, revisitable); never to an external guest (structural, three layers). Unblocks per-developer API keys for the Phase 20 sync CLI.
- **Comment search + mentions** (ADR 0003 §C/§D): full-text search over comment bodies and suggestion text, permission-scoped exactly like document search above (RLS backstop, grant-predicate query, never org-wide); `comment_mentions` store-and-display-only join table scoped to people already on the document (no org-directory picker, no delivery/notification — that's the deferred webhooks arc).

Explicitly out of MVP: audit log, webhooks, Slack/Teams, diagram diffs, data residency, any AI-on-content feature (needs ADR + opt-in).

Post-MVP exploration (needs dreaming + ADR): external guest sharing — consulting firms sharing with client-company emails (guest identity model, per-doc external grants; deliberate exception to org-scoped sharing, isolation principle still absolute). **Hard rule already locked: external guests are capped at read + comment/annotate — never document updates, never new versions, never re-sharing, regardless of grant.** Since ADR 0008 made `edit` grantable at all (extended by ADR 0014 to add `share`), this rule is enforced three independent times: a `share_grants` check constraint (`share_grants_guest_read_comment_only`, migration 0033) forbidding anything but `read`/`comment` on any row carrying a `grantee_email`, refusal at grant creation, and `canEditDocument`/`canShareDocument` returning false for a guest actor before either reads the grant. Also: non-markdown artifacts (PDF, other working files) as first-class or attachment-only.

- **Public Docs Hub** (ADR 0004, Accepted 2026-07-18): a cross-org, unauthenticated, read-only publishing
  surface — the owner's org publishes curated docs (onboarding, runbooks, guides) visible to anyone, no
  login. Deliberately built **outside** the tenant/RLS model (separate non-RLS `public_documents` table,
  separate blob keyspace, SELECT-only DB role) rather than as an exception on `documents` — isolation
  principle untouched. Publish is admin-gated to one configured home org (`PUBLIC_HUB_ORG_ID`); snapshot
  copy, not a live pointer. No comments/threads/anchoring on public docs. See `docs/STATUS.md`.

Tiers, but no prices. `packages/domain/src/tier.ts` carries a real tier lattice (`free` | `team` |
`enterprise`) with per-tier `QuotaLimits`, seat ceilings, guest ceilings and retention profiles, and
the gates on it are enforced in code rather than merely documented — SSO/JIT provisioning, for
instance, is `tier === 'enterprise'` at login. That machinery is genuinely core: it is how _any_
deployment expresses a capability boundary, and a self-hosted instance runs a single org whose
ceilings are unlimited, so it is inert rather than crippling.

What is **not** here is money. There is no price, no billing provider, no subscription lifecycle and
no `BillingProviderPort` anywhere in this repository — attaching a commercial meaning to a tier is
the consuming deployment's job (§7), reached only through `SeatSyncPort`. A self-hoster never
encounters a paywall, and never has to remove one.
