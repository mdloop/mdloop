# ADR 0007 — Suggested-edit acceptance no longer mints a version

- Status: Accepted (2026-07-26, explicit OK per CONSTITUTION §8.5)
- Date: 2026-07-26
- Deciders: Jasdeep (product)
- Relates to: ADR 0002 §C (suggested edits — this ADR supersedes decisions 2 & 3 of that section), CONSTITUTION §5 (anchor model, Core Principle 2), Phase 20 (IDE-agnostic sync CLI, design-only), ADR 0001 (version tombstones — its cap interaction with accept is removed by this ADR)

## Context

ADR 0002 §C made accepting a suggestion equivalent to an upload: `acceptSuggestion` (`packages/app/src/use-cases/suggestions.ts:103-177`) splices `proposedText` into the current version's content server-side and calls `uploadNewVersion` in the same transaction. That assumed mdloop is the document's editing authority.

It usually isn't. A document's canonical content routinely lives outside mdloop — a local file pushed via the web drag-drop upload (`upload-dropzone.tsx`, whole-file replace, the only web-side content-mutation path — confirmed no in-browser body editor exists) or a repo file pushed by an MCP-connected CLI/agent (`packages/cli`, design-only at the time of this ADR). When mdloop splices and uploads on accept, it originates a version the external source file never sees. The next real push from that external source either conflicts with mdloop's self-made version (an optimistic-concurrency guard, comparing `versionSeq` before push) or silently clobbers it. mdloop was quietly appointing itself co-author of documents it doesn't own.

## Decision

1. **Accepting a suggestion is a metadata-only decision, not a mutation.** `acceptSuggestion` flips `comments.suggestion_outcome: open → accepted`, records who/when (existing append-only pattern), and returns. It no longer reads document content, splices, or calls `uploadNewVersion`. `applied_version_id` stays `null` at accept time — the schema already allows this (migration 0016's check is `applied_version_id is null OR suggestion_outcome = 'accepted'`, not "must be set together"), so **no migration is needed**.

2. **Materialization is detected lazily, reusing the existing re-anchor pipeline — not triggered by upload.** `listThreadsWithResolutions` (`packages/app/src/use-cases/reanchor-threads.ts`) already re-anchors every comment against the current version on read, diffing the pinned version against current via `diffVersions`/`resolveTextAnchor`, cached per `(commentId, currentVersionId)`. Extended: for a comment where `kind = 'suggestion' AND suggestionOutcome = 'accepted' AND appliedVersionId IS NULL`, after computing its resolved range, compare `currentSource.slice(resolution.start, resolution.end)` against `comment.proposedText`. Exact match → the diff naturally mapped the anchor's original range onto text that now reads as the proposal, meaning _some_ upload actually applied it → lazily persist via a new `markSuggestionApplied(ctx, commentId, currentVersionId)`. No match (including the common "nobody touched it yet" case, where the range still reads as the original text) → stays `accepted`, resurfaced as pending. This is the same "enforced at read time, no sweep" shape already used for guest-share expiry — no new background job, no hook into any of the three upload paths (manual, MCP, and formerly accept).

   Match is **exact string equality only**, not fuzzy. Core Principle 2 says never guess — a suggestion is "applied" only when the text actually says what was proposed, not approximately. An external edit that applies the same change with different wording never flips to `applied`; it stays honestly `accepted`, forever if need be.

3. **Consuming clients discover pending work through the existing feedback bundle, not a new tool.** `GET /documents/:id/feedback-bundle` (and its MCP twin) grows an `acceptedPendingSuggestions` field: anchor + `proposedText` + accepted-by/at, for every suggestion in the state described in (1). Whoever owns the real edit path for that document — a human re-uploading via drag-drop, or (once Phase 20 ships) the CLI/agent pushing to the source file — reads this list and applies it through the _normal_ upload path, same as any other edit. Rejected: a sixth MCP tool. Same reasoning ADR 0002 already used for `create_comment`'s `proposed_text` param — reuse an existing parity surface over minting a new one.

4. **Authority to accept is unchanged: owner-or-org-admin, same gate as before.** Accept no longer mutates the document, so the Phase 18 guest hard rule ("guests never cause document updates or new versions") no longer _requires_ this gate — structurally, a guest accepting would be no different from a guest submitting a review verdict (ADR 0002 §B decision 5, which guests already may do). Deliberately not loosened here anyway: expanding guest capability is a separate policy call, not a free side effect of a versioning-architecture fix. Left as a considered-but-deferred alternative below; revisit only on concrete demand.

5. **`reject_suggestion` is unchanged.** It was already metadata-only (no document mutation, no read-only gate) — nothing here touches it.

6. **The document body view renders an "as-if-applied" overlay for accepted-but-unmaterialized suggestions — client-side only, never persisted.** For each comment matching the state in (1), the viewer shows the anchored range with the original struck through and `proposedText` inserted in place, directly in the reading pane — not just inside the suggestion card. Computed from `comment.anchor` + `proposedText` against the real current content; the stored bytes are never touched. Reuses the Phase 21.B word-run diff renderer (already builds inline insert/delete visuals for Compare) with a different input pair: real-current vs. hypothetical-if-applied, instead of Compare's real-vs-real. Must be visually distinguishable from a real Compare diff — it is a preview of a decision, not a record of one — and the comment thread badge ("Accepted — pending sync," not "Applied in Leg N") stays visible alongside it. Overlay-without-badge would let a reader believe the file already changed, which is exactly the silent lie Core Principle 2 forbids; both together keep the "gimmick" honest.

## Constitution amendments (applied with this ADR, pending explicit OK)

- **§9 / ADR 0002 cross-reference**: ADR 0002 §C decisions 2 and 3 ("accepting is honesty-gated... extended from display to action" and "accepting is owner-or-org-admin... because accepting _is_ an upload") are superseded by this ADR's decisions 1–3. Decision 1 of §C (suggestion is a comment subtype, not a new table) and decision 4 (suggestions count toward the comment cap) stand unchanged.
- **API/MCP parity table** (§5): no new tool. `feedback-bundle` (HTTP + MCP) response shape grows one field, both sides simultaneously, same parity rule as always.
- No RLS/schema change, no new Gherkin money-path required beyond extending the existing suggestion accept-permission scenarios (ADR 0002 §Money-path Gherkin) to assert accept no longer produces a version.

## Consequences

- `AcceptSuggestionResult` shrinks to `{ comment }` — the `version` and `deduplicated` fields go away, since accept no longer uploads. Any MCP/API consumer reading those fields breaks; acceptable pre-1.0, but worth a changelog note since it's a response-shape change on a shipped tool.
- ADR 0001's version-cap interaction with accept ("a full version cap blocks an accept with `version_cap_exceeded`") is removed — accept can never be blocked by the version cap again, because it never creates a version.
- The web "Accept" button stops feeling immediately gratifying: clicking it no longer produces a new Leg, only a status flip plus the decision-6 overlay (visually similar to today's result, but now explicitly labeled as a preview rather than a fact). This is an honest UX shift relative to today's illusion of instant application, not a bug — flag to product/design before shipping the UI change, since users may currently expect Accept to "just work" with no distinction drawn.
- A suggestion can stay `accepted`-but-unmaterialized indefinitely if nobody ever pushes the matching real edit — same as the "no sweep" precedent elsewhere, not a data-loss risk (the decision + `proposedText` are durably stored rows), but there's currently no "un-accept" path back to `open` if someone changes their mind after accepting but before it lands. Not solved here — flag as a known gap, revisit only if it comes up in practice.
- Squash/`squash_open` design (explored earlier in this thread — batching consecutive accepts into one amended-in-place Leg) is now moot and should not be built: since accept never creates a Leg, there is nothing to squash. Whatever real edit eventually lands closes out however many pending accepts it happens to satisfy, for free.

## Alternatives considered

- **Squash consecutive accepts into one amended-in-place Leg** (`squash_open` flag, explored earlier): rejected — it batches the symptom (too many versions from too many accepts) without fixing the cause (mdloop originating content it doesn't own). Also introduces the first ever mutable-while-open version in the codebase, a bigger invariant break than this ADR requires for a smaller actual win.
- **Trust the next uploaded version unconditionally** (mark all pending-accepted suggestions `applied` the moment _any_ new version lands, without checking content): rejected — breaks Core Principle 2 outright. A client could upload an unrelated edit and every pending suggestion would be marked applied without ever having been applied, which is exactly the kind of silent lie the anchor/comment model exists to prevent.
- **Open up guest accept authority as part of this change** (decision 4's deferred alternative): rejected for now — it's a legitimate follow-on given accept is no longer a mutation, but bundling a permission-boundary change into a versioning-architecture ADR risks approving one without scrutinizing the other on its own merits.
